# Регламент розробки: 2 робочі місця × 2 ШІ-агенти (послідовно)

> **Навіщо цей файл.** Один репозиторій (`dev`), два локальні клони на двох машинах,
> по одному ШІ-агенту на кожній. Агенти працюють **не одночасно**, а по черзі, передаючи
> «естафету». Мета — щоб різні фічі не ламали одна одну, спільний staging не конфліктував,
> а кожен агент завжди знав, у якому стані залишив справу попередній.
>
> Читати РАЗОМ із `PROJECT_OVERVIEW.md` (архітектура) і `TODO.md` (план, SSOT задач).
> Цей файл описує **лише координацію між машинами**, не технічну архітектуру.

---

## 1. Ключові факти середовища (чому правила саме такі)

- **Спільний staging.** `make test` і `./deploy.sh` б'ють у **один** VPS: один каталог
  `/home/onivan/cohbbot-dev`, один сервіс `expensebot-dev.service` (порт 8001), одна БД
  `cohbbot_db`. Два агенти, що одночасно тестують/деплоять, зіткнуться.
- **Деплой = push у `deploy-dev`** (bare-репо на VPS) → хук `post-receive` робить
  `git reset --hard` + рестарт юніта. Деплоїться **HEAD поточної гілки**.
- **`origin` (GitHub) — канал синхронізації** між двома машинами. Пуш у `origin` **не деплоїть**.
- **Єдине спільне середовище для обох агентів** — git-репозиторій. Тому стан координації
  («хто зараз працює», «що і як передано») живе **у файлах, закомічених у `dev`**.

> Висновок: координація = **один активний агент у часі** + **лок/борд у git** + **явна передача**.

---

## 2. Правила (не ламати)

1. **Один активний (ACTIVE).** У будь-який момент лише один клон/агент має право змінювати
   `dev`. Інший — **PASSIVE**: може `git pull` і читати, але MUST NOT редагувати, комітити
   в `dev`, пушити `dev` чи деплоїти.
2. **Борд — джерело істини про поточний статус.** Без захопленого лока роботу не починати.
3. **`dev` завжди придатна до деплою** в момент передачі. Незакінчене — на гілці, не в `dev`.
4. **Staging — сингулярний ресурс.** `make test` / `./deploy.sh` виконує лише ACTIVE.
5. **Не переписувати опубліковану історію `dev`**: ніяких `git push --force`, `reset --hard`
   в робочому клоні, rebase вже запушених комітів `dev`. Синхронізація — `git pull --rebase`
   (переносить лише **свої неопубліковані** коміти).
6. **Гарячі правки на VPS заборонені** (див. `PROJECT_OVERVIEW.md` §I) — вони блокують наступний деплой.
7. **Не запускати сервер/скрипти локально.** Усе, що залежить від БД/сервісу, — на VPS
   (`make test`, `make logs`, `make status`). Агент лише редагує файли й комітить.
8. **`.env` і `.vps.env` існують лише локально** в кожному клоні (у `.gitignore`, `chmod 600`).
9. **Естафета = борд + явний «наступний крок».** Поки передача не записана, робота не завершена.

---

## 3. Ідентичність робочого місця

Кожен клон має **локальний** файл `.workstation` у корені (у `.gitignore`), один рядок:

```
ws-a
```

- `ws-a` / `ws-b` — фіксовані ID двох машин (заповнює людина одноразово на кожній машині).
- Файл **не комітиться** (він локальний і різний на кожній машині).
- Агент на старті сесії читає його: `cat .workstation`. Якщо файлу нема — **запитати
  людину** й попросити створити (`echo ws-a > .workstation`), не вигадувати ID.
- Мапа «ID → машина/ОС/клон» ведеться людиною поза git (у нотатках), напр.:
  `ws-a` = Windows 11, `ws-b` = Ubuntu.

## 5. Формат `docs/coord/BOARD.md`

Верхній блок — **поточний лок** (рядки `- ключ: значення`, легко читаються очима й агентом):

```
## 🔒 Поточний статус

- state: FREE            # FREE | BUSY
- owner: —               # ws-a | ws-b | —
- task: —                # ID із TODO.md (напр. J2)
- branch: —              # feat/j2-user-cash
- since: —               # UTC ISO, напр. 2026-09-09T13:40:00Z
- note: —                # 1 рядок: що робиться / на чому зупинились
```

Нижче — **журнал передач**, лише дописування (**append-only**, чужі записи не видаляти):

```
### 2026-09-09T13:40Z · ws-a → передача (task J2)
- Коміти: dev @ ab12cd3 (+ feat/j2-user-cash, merged)
- Стан: тести ✅, staging active @ ab12cd3
- Зроблено: вкладка «💰 Кошти» (read-only), «Бюджет»→«Ліміти»
- Ручні кроки людини: pip install -r requirements.txt (додано X); міграцій немає
- Відкрите/ризики: ...
- Наступний крок: J4 — огляд по роках і місяцях
```

## 6. Старт сесії (чекліст агента)

1. **Ідентифікація:** `cat .workstation` → `ME`. Нема — спитати людину (§3).
2. **Чистий стан:** `git fetch origin && git status -sb`. Є незакомічені зміни — **STOP**,
   спитати людину (не «підмітати» чужі/незрозумілі правки).
3. **Прочитати борд:** `docs/coord/BOARD.md`. Визначити лок:
   - `state: FREE` → захопити (крок 4);
   - `state: BUSY`, `owner: ME` → наш «завислий» лок (після збою) → перезахопити, оновивши `since`;
   - `state: BUSY`, `owner != ME`, `since` свіжий (**< 12 год**) → **STOP**: доповісти
     «лок тримає `<owner>` з `<since>`, задача `<task>`» і чекати вказівки людини;
   - `state: BUSY`, `owner != ME`, `since` старий (**≥ 12 год**) **АБО** людина явно сказала,
     що інша машина завершила/вимкнена → **takeover**: дописати в журнал рядок
     `stale takeover: <owner> з <since>` і перезахопити.
4. **Захоплення лока:** у борді виставити `state: BUSY`, `owner: ME`, `task`, `branch`,
   `since` = `date -u +%Y-%m-%dT%H:%M:%SZ`, `note`. Далі:
   ```
   git add docs/coord/BOARD.md
   git commit -m "chore(coord): claim <task> (<ME>)"
   git push origin dev
   ```
   push відхилено → `git pull --rebase origin dev` (лише свої коміти) → повторити push.
5. **Синхронізація коду:** `git pull --rebase origin dev`.
6. **Онбординг:** прочитати `PROJECT_OVERVIEW.md`, актуальний `TODO.md` і **«Наступний крок»**
   з останнього запису журналу. Якщо задача не очевидна — уточнити в людини.
7. Працювати згідно §7.

---

## 7. Робота (гілки, коміти, тести)

- **Гілки.** Задача, що не завершується за одну сесію, ведеться на
  `feat/<taskid>-<slug>` (або `fix/<taskid>-<slug>`), напр. `feat/j2-user-cash`.
  Дрібний фікс можна комітити прямо в `dev`, але тоді `dev` мусить лишатися зеленою (§8).
- **Коміти** — дрібними кроками, одразу після перевірки. Стиль:
  `feat(scope): …`, `fix(scope): …`, `docs(scope): …`, `chore(coord): …`.
- **Тести:** `make test` (на VPS). Перед мержем у `dev`/деплоєм — тести мають бути зелені.
- **Схема БД** (`schema.sql` + `ensure_*_schema()`): зміни робити **ідемпотентними** й
  завершувати в межах однієї сесії (див. §9 «важкі задачі»).
- Після кожного логічного кроку — коміт. Незакомічених правок не лишати (правило проєкту).

---

## 8. Передача (чекліст агента наприкінці сесії)

1. **Зелений стан.** Якщо задача завершена — `make test` зелений, і `dev` готова до деплою.
   Якщо **не** завершена — перенести незакінчене на гілку (`git switch -c feat/...`), а `dev`
   повернути до останнього зеленого коміту (**без** rewrite історії: мерж/черрі-пік, не reset
   опублікованого). Гілку явно назвати в записі журналу.
2. **Деплой (за потреби).** Лише ACTIVE і лише коли `dev` — те, що має жити на staging:
   `./deploy.sh`. Переконатися, що `status` показує `active` і HEAD на VPS збігається.
3. **Запис у журнал** (§5, шаблон): коміти, стан, зроблено, **ручні кроки людини**
   (pip install / міграція / `.env` / рестарт), відкрите/ризики, **наступний крок**.
4. **Відпустити лок:** `state: FREE`, `owner: —`, `task/branch/since/note: —`.
5. **Коміт і пуш:**
   ```
   git add -A && git commit -m "chore(coord): release <task> — handoff (<ME>)"
   git push origin dev
   ```
6. **Доповісти людині:** що задеплоєно (SHA), які ручні кроки потрібні, який наступний ID.

## 9. Розподіл напрямів (щоб різні фічі не билися)

Навіть послідовно варто мінімізувати тертя. Орієнтир (не жорстко):

| Машина | «Смуга» (напрями TODO) | Примітка |
|---|---|---|
| `ws-a` | J (Кошти ЦН), A (AI) | cash-фічі + розпізнавання |
| `ws-b` | B (перевитрати), C (дублікати), E (PDF), H (права) | сповіщення/звіти/безпека |

Правила смуг:
- **Важкі задачі (зміна схеми БД: D1, D2, G1, J4) — робити «наодинці»**: не передавати
  естафету з незавершеною схемою; `ensure_*_schema()` має бути ідемпотентним і вже
  застосованим до передачі.
- Беручи задачу, звіряй, чи не торкається вона файлів із **незамерженої** гілки попередника
  (шукай згадку такої гілки в журналі). Якщо так — спершу доведи ту гілку до `dev` або узгодь
  з людиною.
- Одна задача = один ID із `TODO.md`. Не змішувати дві фічі в одній сесії без потреби.

## 10. Конфлікти та відновлення

- **push відхилено (remote попереду):** `git pull --rebase origin dev` → за потреби розв'язати
  конфлікт → `make test` → `git push origin dev`. Ніколи не `push --force` у `dev`.
- **Завислий лок (машина вимкнена під час BUSY):** див. §6.3 — takeover зі свіжим `since`
  і рядком `stale takeover` у журналі.
- **Випадково обидві машини ACTIVE:** та, що ще **не** пушила змін, негайно **STOP**:
  `git stash` (або перенести в гілку) → `git pull --rebase` → показати людині. Право писати
  має лише `owner` з борду; решта узгоджує передачу.
- **Забруднений `dev` перед деплоєм:** хук/`deploy.sh` відмовляться. Зберегти як патч
  (`git diff > ~/hotfix.patch`), внести комітом, очистити каталог — не робити ручних правок на VPS.

## 11. Антипатерни (чого НЕ робити)

- Працювати без захопленого лока / паралельно на двох машинах.
- Комітити в `dev` незакінчену фічу, що ламає запуск.
- `git push --force` / `reset --hard` опублікованої `dev`.
- Деплоїти з PASSIVE-машини або без зеленого `make test`.
- Робити ручні правки на VPS (ламають наступний деплой).
- Видаляти/переписувати чужі записи журналу передач.
- Заводити додаткові файли стану поза бордом.

## 12. Швидкі команди (шпаргалка)

```bash

git push origin dev                           # публікація коду й борду
```
